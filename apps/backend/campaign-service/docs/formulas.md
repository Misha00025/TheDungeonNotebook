# Formulas, virtual fields, and computed sheets

All routes are scoped to `/api/campaigns/{campaignId:int}`. Requests use `Content-Type: application/json` and the required JSON `X-Subject` header described in [the campaigns API](campaigns.md). A global Admin, matching Group, or campaign administrator may write definitions. Definition reads use `Access:MembersCanReadDefinitions`; when enabled (default), a campaign member can read definitions. Character routes use the same character assignment/write rules as [character sheets](characters.md). Campaigns and resources outside the subject's scope return `404`; insufficient scoped rights return `403`.

Example headers:

```http
Content-Type: application/json
X-Subject: {"Type":"User","Id":42}
```

## Formula definitions

Metadata is `{id,key,campaignId,name,metadataRevision}`. `key` is derived from the GUID `id` in `N` format. Metadata revision begins at 1. Formula content is `{campaignId,resourceId,contentRevision,data:{expression,parameters}}`; revisions are independent. There is no formula deletion endpoint.

| Method and path | Request | Rights | Success |
| --- | --- | --- | --- |
| `GET /formulas` | none | definition read | `200` metadata array |
| `POST /formulas` | `{requestId: GUID, name: string, expression: string, parameters: string[]}` | admin | `201` metadata plus `contentRevision:1`; `Location: /api/campaigns/{campaignId}/formulas/{id}` |
| `GET /formulas/{formulaId:guid}` | none | definition read | `200` metadata |
| `PUT /formulas/{formulaId:guid}` | `{name: string, expectedRevision: int64 >= 1}` | admin | `200` metadata with incremented metadata revision; SQL only |
| `GET /formulas/{formulaId:guid}/content` | none | definition read | `200` formula content envelope |
| `PUT /formulas/{formulaId:guid}/content` | `{expression: string, parameters: string[], expectedRevision: int64 >= 1}` | admin | `200` updated envelope with incremented content revision; Mongo CAS only |

`requestId` is a non-empty GUID and becomes the immutable formula ID. Creation checks for published SQL metadata, inserts Mongo `formulaContents`, then publishes SQL metadata. A known published ID is `409 already_published`; an existing prepared Mongo document is `409 content_already_prepared`; uncertain SQL publication is `503 publication_outcome_unknown` with the resource ID. Prepared content is not deleted and publication is not retried automatically. A published formula whose content document is unavailable returns `503 content_unavailable`. SQL metadata rename never changes formula content.

`expression` must be non-whitespace and parse as NCalc; `parameters` is a required array (empty is valid) of unique, non-empty, case-sensitive names. Every parameter referenced by the expression must be declared. Saving validates syntax and declarations but does not evaluate the expression. Invalid formula input returns `400 invalid_formula` with a safe message. Formula contents have no application value-size limits.

## Template virtual fields

| Method and path | Request | Rights | Success |
| --- | --- | --- | --- |
| `GET /template/virtual-fields` | none | definition read | `200 {contentRevision,virtualFields}` |
| `PUT /template/virtual-fields` | `{expectedRevision:int64 >= 0, virtualFields:VirtualFieldInput[]}` | admin | `200 {contentRevision,virtualFields}` |

These paths are relative to `/api/campaigns/{campaignId}` and address the campaign's single canonical template. The PUT replaces the entire active virtual-field set in the shared campaign-template Mongo content document and preserves template description and base fields. It uses the same content revision as `PUT /template/content`: a new empty template starts at logical revision `0`, and its first successful base or virtual-field PUT creates the document at revision `1`. The input shape is `{id?,key,title,description,resultType,formulaId,bindings,parentBaseFieldId?,parentVirtualFieldId?}`. `resultType` is `Integer` or `Number` (`NumericResultType`); `formulaId` must identify a published formula in this campaign. `bindings` maps exact formula parameter names to `{kind:"Base"|"Virtual",fieldId:GUID}`; each reference `kind` is explicitly required and omission is invalid. Parent references provide the special parameter named `parent` and are `{parentBaseFieldId}` or `{parentVirtualFieldId}`. A parent is optional and may be supplied only once; it cannot also be supplied as `bindings.parent`.

New field IDs are generated by the service and included in the response. Base fields and virtual fields are separate types with separate GUID identities; matching `key` values across them are allowed. Existing virtual-field IDs must be active in the set being updated; their keys are immutable. Virtual keys are unique within the submitted virtual-field set, independently for template and custom sets. Every binding key must be declared by the formula. Explicit references are checked even when their parameter is unused by the expression. Template fields may reference active base fields and active template virtual fields only. Cycles may be saved and are reported by computed-sheet diagnostics. To reference a newly created field, save it first, then issue another full-set PUT using its returned ID. Stale revisions return `409 content_revision_conflict` before Mongo replacement.

## Character virtual fields and overrides

| Method and path | Request | Rights | Success |
| --- | --- | --- | --- |
| `GET /characters/{characterId:guid}/custom-virtual-fields` | none | character read | `200 {contentRevision,virtualFields}` |
| `PUT /characters/{characterId:guid}/custom-virtual-fields` | `{expectedRevision:int64 >= 1,virtualFields:VirtualFieldInput[]}` | character write | `200 {contentRevision,virtualFields}` |
| `GET /characters/{characterId:guid}/virtual-overrides` | none | character read | `200 {contentRevision,overrides}` for active template targets only |
| `PUT /characters/{characterId:guid}/virtual-overrides/{virtualFieldId:guid}` | `{expression:string,expectedRevision:int64 >= 1}` | character write | `200 {contentRevision}` |
| `DELETE /characters/{characterId:guid}/virtual-overrides/{virtualFieldId:guid}?expectedRevision={revision}` | required query `expectedRevision:int64 >= 1` | character write | `200 {contentRevision}` |

Custom fields are replaced as a whole and stored separately in each character's sheet document; template definitions are never copied into a character. Custom field and override operations retain their character-document revision contract of int64 >= 1. Custom fields can reference active base/virtual fields from the campaign's single template and active custom virtual fields. They use the same IDs, key, formula, binding, and parent rules. Matching keys across base, template virtual, and custom virtual field sets are allowed; keys need only be unique within the set being updated. A stale content revision returns `409 content_revision_conflict`.

Overrides only target active template virtual fields. The override expression is parsed and its used parameters must be declared by the field's current formula; the field's bindings and parent references remain unchanged. PUT replaces only that target's override. DELETE removes it, so the current formula content is used on the next calculation, not a stored formula snapshot. Removed-target overrides may remain stored but are omitted from GET. Both operations update the character sheet revision through Mongo CAS.

## Computed sheet

`GET /characters/{characterId:guid}/computed-sheet` requires character read access and returns `200`:

```json
{"contentRevision":3,"templateContentRevision":5,"formulaContentRevisions":[{"id":"...","contentRevision":2}],"description":"...","baseFields":[],"virtualFields":[{"id":"...","key":"total","title":"Total","description":"","resultType":"Integer","value":12,"diagnostic":null}]}
```

Only active effective base fields are included; hidden/deleted saved base values and raw formula expressions are not exposed. The calculation reads each relevant formula metadata/content at most once per request, then evaluates without writes. Each returned formula revision identifies the content version observed for that formula; the set is not a global cross-document snapshot. The existing `/characters/{characterId}/sheet` remains base-fields-only.

NCalc is used as a parser/evaluator, never C#, JavaScript, or `eval`. Standard NCalc math functions are available. Built-in function names are case-insensitive; formula parameter names are case-sensitive. One outer `{...}` around a whole expression is accepted. String-to-number coercion and boolean arithmetic are disabled. Numeric results are only `Integer` or `Number`: integers are int64; a fractional integer result is rounded to nearest with half values away from zero (`2.5`→`3`, `-2.5`→`-3`). Number results are finite IEEE-754 doubles and are not rounded. Boolean, string, and null final results are errors.

Calculation diagnostics are returned with HTTP `200` per virtual field and do not prevent independent fields from calculating. Codes include `missing_formula`, `syntax_error`, `unknown_parameter`, `missing_input`, `unknown_reference`, `cycle`, `dependency_error`, `type_error`, and `arithmetic_error`. Messages are safe and do not include raw expressions, values, or exception text. Missing SQL formula metadata yields `missing_formula`; missing Mongo content for a published formula returns `503 content_unavailable`; storage/network failures remain safe `503` dependency errors. Request validation returns `400`, rights errors `403`, missing/cross-campaign resources `404`, stale revisions `409`.
