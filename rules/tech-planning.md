# Планирование крупных изменений — Tech Planning

## Принцип: двухшаговое планирование в одном файле

Любое крупное изменение (рефакторинг, миграция, новый функционал) планируется одним файлом в папке `plans/`. Файл содержит две обязательные секции.

### Секция 1: Целевое состояние (к чему идём)

Отвечает на вопрос "что мы хотим получить".

Содержит:
- **Проблемы и мотивация** — что именно не так с текущим состоянием, почему это важно чинить
- **Целевая архитектура** — как должно работать: pipeline, компоненты, их роли
- **Hard constraints** — что НЕЛЬЗЯ менять (базы данных, response-модели, внешние контракты, выбранные технологии)
- **Контракт API** — что видит клиент, что можно менять, что нельзя менять
- **Риски** — что может пойти не так, митигация

Формат: только концептуальное описание, без кода.

### Секция 2: Миграционные фазы (как туда придём)

Отвечает на вопрос "какими шагами мы туда перейдём".

Содержит:
- Разбивку на крупные фазы
- Каждая фаза — один git commit
- Для каждой фазы: что меняется концептуально, почему не сломаются тесты
- Каждая фаза должна быть самодостаточна — после неё сервис работоспособен, сквозные тесты (api-gateway) проходят с 0 ошибок
- Фазы упорядочены по зависимостям: нельзя удалить старый механизм, пока новый не покрывает все его кейсы
- Если нужно — фаза "дуализма" (оба механизма параллельно) перед фазой удаления старого
- Если нужно — фаза отложенных задач (deferred, documented risk)

Формат: только концептуальные описания, без кода.

## Почему такой подход

- Предотвращает half-baked решения: нельзя начать писать код, не понимая куда идём
- Сохраняет архитектуру целостной: каждое изменение вписано в общую картину
- Гарантирует прохождение тестов на каждом шаге: фазы спроектированы с учётом braking changes = 0
- Отделяет "что" от "как": это разные когнитивные задачи, их нельзя решать одновременно

## Когда нужен

- Рефакторинг архитектуры
- Миграция данных или схем
- Введение нового механизма, который заменяет старый
- Любое изменение, которое затрагивает >3 файлов или >1 сервиса

## Когда не нужен

- Исправление одного бага
- Добавление одного эндпоинта по существующему паттерну
- Косметические изменения

## Важно

- План пишется без кода (только концептуально)
- План удаляется после завершения всех фаз (папка `plans/` содержит только активные планы)
- Каждая фаза проходит тесты — это обязательное условие
- Если между фазами обнаруживается неучтённая зависимость — возвращаемся к секции 2, корректируем фазы
- Первая фаза может быть подготовительной (например, мониторинг или дуализм)
- Последняя фаза — удаление старого механизма и финальный прогон тестов
