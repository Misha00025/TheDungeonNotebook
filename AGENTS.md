# Project Information

Current behavior is established by source code, tests, and public HTML documentation. This file does not record the project's architectural state.

## Границы задачи

- Реализуйте запрошенную функцию или сервис, а не самостоятельно выбранную полную платформу вокруг него.
- Не добавляйте продуктовые политики, ограничения эксплуатации и требования к deployment без запроса пользователя.
- Не расширяйте задачу ради предполагаемых будущих потребностей. Найденные смежные проблемы сообщайте отдельно и не исправляйте попутно без согласования.
- Не подменяйте отдельную задачу архитектурной переработкой всего связанного контура.

## Принятие решений

- Различайте необходимый механизм и политику его применения. Наличие механизма не даёт права навязывать режимы эксплуатации и ограничения окружений.
- Используйте стандартные возможности библиотек и фреймворка, прежде чем писать собственные валидаторы, маршрутизаторы и протокольные механизмы.
- Каждая дополнительная проверка должна обеспечивать конкретное требование задачи или корректность используемого протокола. Не добавляйте проверки только потому, что это технически возможно.
- Не вводите ограничения, меняющие существующие контракты зависимых сервисов, без согласования.
- Не превращайте каждую неопределённость в новый механизм, настройку или специальный режим. Действительно блокирующие вопросы задавайте пользователю.

## Конфигурация

- Подключения, эксплуатационные параметры и выбираемые политики должны задаваться конфигурацией, а не константами и условными ветками исходного кода.
- Изменение конфигурации не должно требовать редактирования исходников и пересборки приложения.
- Разумные значения по умолчанию допустимы. Не выдавайте произвольные жёсткие ограничения за требования протокола.
- Проверяйте корректность конфигурации, а не соответствие самостоятельно придуманной модели эксплуатации.
- Не навязывайте единственный способ передачи настроек или секретов, если задача этого не требует.

## Структура и поставка

- Понятно разделяйте исходники, конфигурацию, тесты и файлы сборки.
- Минимальные Dockerfile, compose.yaml, entrypoint.sh и .dockerignore для сборки и запуска сервиса допустимы и являются частью поставки, когда задача предусматривает такой запуск. Это не разрешение строить окружающую инфраструктуру.
- Не создавайте локальные комплексы IdP, баз данных, ingress и зависимых сервисов без отдельного запроса.

## Проверка и откат

- Тестирование ограничивается unit-тестами, если пользователь не запросил другие проверки. Браузерные тесты не добавляйте.
- Выполняйте релевантную сборку после изменений кода. Не объявляйте непроведённые проверки успешными.
- При откате удаляйте только конкретные излишки, а не все связанные с ними полезные файлы. Не затрагивайте чужие изменения и ценные данные.

## Начало нового сервиса

- Любой новый сервис начинается с настройки окружения штатными средствами (dotnet, python и т.д.)
- Никогда нельзя начинать новый проект сразу с написания кода 
- Код пишется только после того как окружение подготовлено
